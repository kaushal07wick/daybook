daybook

A local Mac service that reads every AI-coding session you run — Claude Code, Codex, and whatever comes next — and turns it into daily and weekly digests of what you actually did: the systems, the numbers, the tech, the facts. Yours, on your disk, summarised by any LLM you choose.

1. Problem

If you work through an AI coding agent all day, the agent's transcript is your work log — it's the only place that records which server you fixed, what the throughput number was, which library you migrated to, and when. But those transcripts sit as gigabytes of JSONL under ~/.claude/projects and ~/.codex/sessions, scattered across dozens of repos, and nobody reads them back.

The consequence: when it's time to write a resume bullet, a weekly update, a build-in-public post, or just answer "what did I do in August?", the facts are gone from memory and buried on disk. On this Mac alone: 147 Claude Code transcripts (620 MB) across 14 project dirs + 55 Codex sessions, accumulated in under three months, and zero of it is queryable.

2. Who it's for

Primary — the heavy agent user

Runs Claude Code / Codex 8–16 h/day across many repos and remote boxes. Wants a digest, not a search box. Cares that client data never leaves the machine unless they say so.

Secondary — the OSS adopter

Installs via brew, points it at their own LLM (Ollama, OpenAI, Anthropic, OpenRouter, Groq…), never touches Go. Expects it to just run and stay out of the way.

3. Goals & non-goals

Goals

  • P0Continuously ingest every new session from all supported agents with no manual step.
  • P0Produce a daily digest (narrative + structured facts) and a weekly digest that rolls the days up.
  • P0Work fully offline with a local model (Ollama) by default; cloud providers are one config block away.
  • P0Never send unscrubbed transcript text to a cloud provider.
  • P1Backfill the whole history on first run, resumable, without melting the laptop.
  • P1Keep a running skills & facts ledger (tech terms, numbers, hostnames, projects) as a by-product of every digest — the raw material for a resume.
  • P1Menubar presence: today's digest one click away.
  • P2Export: Markdown, JSON, and "resume bullets" view.

Non-goals (v1)

  • Not a chat-with-your-history product. No RAG, no vector DB. Full-text search is enough.
  • Not a time tracker. We infer activity from transcripts, we don't watch windows.
  • Not multi-user or cloud-synced. One Mac, one user, one SQLite file.
  • Not a resume generator. It produces the inputs to a resume, not the document.
  • No Linux/Windows in v1 (design doesn't preclude it — only the launchd installer and menubar are Mac-specific).

4. User stories

  1. "It's 11 pm. I open the menubar and read a 10-line summary of today with the numbers in it, and I post two of the lines on X."
  2. "Monday morning I open Week 38 and see, per project, what shipped, what broke, and which hosts I touched."
  3. "I'm updating my resume. I open the ledger, filter by tech, and get 'TensorRT, DeepStream, ByteTrack, NVDEC, WireGuard, k3s, pgvector…' with dates and session links."
  4. "I install it on a fresh Mac, run daybook install, it finds Ollama and starts backfilling. I go to sleep. In the morning three months of digests exist."
  5. "I want better summaries. I add [providers.claude] with an API key, set it as default, and the scrubber strips IPs/secrets/customer names before anything is sent."
  6. "Codex/Cursor/opencode changes its log format. I add one parser file; nothing else changes."

5. Functional requirements

5.1 Ingest

IDRequirement
F-1Watch ~/.claude/projects/**/*.jsonl and ~/.codex/sessions/**/*.jsonl with fsnotify; on change, tail from the last byte offset. Restart-safe: offsets persisted.
F-2Parser per source normalises lines into events: (session_id, ts, role ∈ user|assistant|tool, kind, text, tool_name, cwd). Thinking blocks, token reminders, attachments are dropped. Tool results truncated to 2 KB.
F-3Session is closed when its file has had no writes for 30 min (configurable). Only closed sessions are summarised; still-open ones show as "in progress" in today's view.
F-4Backfill: daybook backfill ingests everything present, then summarises oldest-first with a concurrency cap (default 1 for local models, 4 for cloud). Resumable at any point.
F-5New sources are added by implementing one Source interface (glob + line parser). Claude Code and Codex ship in v1.

5.2 Summarise

IDRequirement
F-6Session summary — one LLM call per closed session producing strict JSON: headline, project, work[], tech[], numbers[], facts[], hosts[], outcome. Retried once on invalid JSON; stored raw on second failure so nothing is lost.
F-7Long sessions are chunked at ~24k tokens; chunk summaries are reduced into the session summary (map-reduce). Chunk size is per-provider config.
F-8Daily digest — generated at 23:55 local (and on demand) from that day's session summaries: 5–15 line narrative grouped by project + merged structured lists.
F-9Weekly digest — Sunday 23:58 from the 7 daily digests. Same shape, plus "themes".
F-10Digests are regenerable: daybook digest --day 2026-09-21 --force after switching providers.
F-11Ledger — every tech, number, host, project term from session summaries is upserted into a term table with first-seen, last-seen, count, and session links. No LLM call; pure aggregation.

5.3 Providers

IDRequirement
F-12Two adapters cover the market: OpenAI-compatible chat completions (Ollama, OpenAI, Groq, OpenRouter, Together, DeepSeek, LM Studio, vLLM…) and Anthropic Messages. Anything else is a base_url change.
F-13Config: ~/.config/daybook/config.toml. Each provider block has type, base_url, model, api_key_env, cloud (bool), max_input_tokens. Keys are read from env/Keychain, never stored in the file.
F-14First run with no config: probe localhost:11434; if Ollama is present, pick the best installed model and write a default config. If absent, print exactly one line telling the user what to install or configure.

5.4 Surface

IDRequirement
F-15Web UI on 127.0.0.1:7331, server-rendered, embedded in the binary. Pages: Today, Day, Week, Ledger, Sessions, Settings (read-only view of config + provider health).
F-16Full-text search (SQLite FTS5) over session summaries and digests.
F-17Menubar icon (P1): shows today's headline count, opens the UI, shows "summarising 3/12…" while busy.
F-18CLI: daybook install | uninstall | serve | backfill | digest | status | export. install writes the launchd plist under ~/Library/LaunchAgents and starts it.
F-19Export: daybook export --week 2026-W38 --format md|json and a ledger export.

6. Non-functional requirements

  • Idle cost: <0.5 % CPU, <60 MB RSS when watching. No polling — fsnotify only.
  • Backfill cost: summarising with a local 7B model must not starve the foreground; run at nice 10, concurrency 1, pausable.
  • Durability: single SQLite file in WAL mode at ~/Library/Application Support/daybook/daybook.db. Crash mid-summary loses at most that one summary.
  • Idempotence: re-ingesting the same file is a no-op; re-running a digest with the same provider+model is a no-op without --force.
  • Zero cgo, single static binary: so brew install and cross-compiling stay trivial. (Menubar is the one exception — see stack.)
  • Observability: structured logs via log/slog to ~/Library/Logs/daybook/, plus daybook status showing queue depth, last ingest, provider latency.
  • Tests: parser fixtures from real (scrubbed) transcripts; provider adapters tested against an httptest fake; scrubber has a golden-file test. CI runs go vet, staticcheck, golangci-lint, tests with race detector.

7. Architecture (summary)

~/.claude/projects/**/*.jsonl ─┐ ~/.codex/sessions/**/*.jsonl ─┤ fsnotify ▼ ┌─────────────┐ Source interface │ ingest │ (claude, codex, …) └──────┬──────┘ ▼ events, sessions ┌─────────────┐ │ sqlite │ WAL · FTS5 · pure-Go driver └──┬───────┬──┘ closed sessions ▼ ▲ summaries, digests, ledger ┌─────────────┐ scrub() if provider.cloud │ summarizer │ ──────────────► Provider │ (queue) │ map-reduce ├ openai-compatible └──────┬──────┘ └ anthropic ▼ ┌─────────────┐ │ scheduler │ 23:55 day · Sun 23:58 week └──────┬──────┘ ▼ http :7331 ◄──── ┌─────────────┐ ────► menubar (P1) (html/template) │ serve │ └─────────────┘

Everything above is one process, one binary, one DB. Packages map 1:1 to boxes: internal/source, internal/store, internal/summarize, internal/provider, internal/scrub, internal/schedule, internal/web, cmd/daybook. Full detail lives in docs/ARCHITECTURE.md.

8. Data model

sources    (id, kind, path UNIQUE, byte_offset, mtime, last_seen)
sessions   (id PK, kind, project, cwd, started_at, ended_at, closed, n_events)
events     (id, session_id, ts, role, kind, tool_name, text)          -- text ≤ 2 KB for tool results
summaries  (session_id PK, provider, model, json, created_at)         -- F-6 shape
digests    (period 'day'|'week', key, provider, model, json, md, created_at, PK(period,key))
terms      (term, kind 'tech'|'number'|'host'|'project', first_seen, last_seen, n, PK(term,kind))
term_links (term, kind, session_id)
fts        (FTS5 over summaries.json + digests.md)

9. Privacy model

Rule: raw transcript text goes to a provider marked cloud = false as-is. For cloud = true it passes through scrub() first, always, no flag to disable it.

scrub() is deterministic regex + a user-supplied denylist: IPv4/IPv6, emails, URLs with credentials, bearer/API-key shapes (sk-, AKIA, ghp_, xox, 32+ hex/base64 runs), password=… / -p … / token: patterns, SSH private-key blocks, and any string listed in [privacy].redact = [...] (customer names, hostnames). Replacements are stable placeholders (<ip-3>) so the model can still reason about "the same host". The scrubbed text is never stored; only the summary is.

10. Stack decision

ConcernChoiceWhy (and what was rejected)
LanguageGo 1.23+Single static binary, launchd-friendly, trivially brew-able, excellent stdlib for HTTP/JSON/embed, matches the author's existing daemons. Rust: slower to iterate, no gain here. Python: venv hell for adopters. Swift: no server/LLM ecosystem.
DBSQLite via modernc.org/sqlitePure Go, no cgo, FTS5 included. Postgres is absurd for one user.
File watchingfsnotifyKqueue under the hood; the only sane choice on macOS.
ConfigTOML via BurntSushi/tomlHuman-editable, comments allowed; YAML's footguns not worth it.
LLM clientshand-written, net/httpTwo endpoints, ~200 lines total. SDKs add versions to chase and hide the request shape.
Web UIhtml/template + embed, ~100 lines vanilla JSNo build step, no node. It's five read-mostly pages. HTMX/templ rejected as unneeded.
Schedulerin-process time.Timer loopTwo cron entries; a cron library is overkill.
MenubarP1: minimal Swift .app that shells out to daybook status --json and opens the UIKeeps the Go binary cgo-free. fyne/systray would drag cgo into every build.
Packaginggoreleaser → Homebrew tap + GitHub releaseStandard, zero custom scripts.
Quality gategolangci-lint, staticcheck, race tests, conventional commits, CI on every PRNon-negotiable for an OSS repo.

12. Success metrics

  • Day-1: full backfill on this Mac completes overnight on a local 7B model with zero manual intervention.
  • Daily: the author reads the digest ≥5 days/week (it's actually useful, not just running).
  • Quality: ≥90 % of numbers in a digest trace to a real line in a transcript (spot-checked on 20 sessions).
  • OSS: a stranger goes from brew install to first digest in under 10 minutes, per README alone.

13. Open questions

  • Session "closed" heuristic — 30 min idle is a guess; Claude Code resumes sessions days later. Treat a resumed session as a new segment for digest purposes?
  • Which local model is the default pick? Candidates: qwen2.5:7b, llama3.1:8b, gemma2:9b. Needs a 10-session bake-off on JSON validity.
  • Should the ledger de-duplicate near-synonyms ("TensorRT" / "TRT" / "tensorrt") with a normalisation table, or leave it raw in v1?
  • Do we ingest ~/.claude/history.jsonl (prompt history) too, or is the project transcript enough? (Leaning: enough.)
